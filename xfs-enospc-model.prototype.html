XFS ENOSPC‑with‑free‑space — a driveable model

Question this answers: on a sparse=1 XFS (the ROSA HCP default, which customers can’t change), can creat() still fail with ENOSPC while the disk shows free space (RHEL‑82924)? And why does deleting files not reproduce it while punching/truncating them does?

This is a shrunk‑down, in‑memory model of one XFS: 64 blocks (4 KiB each). Inodes live in clusters. A new inode cluster needs a contiguous run of free blocks — sparse=1 → 2 blocks, sparse=0 → 8 blocks. File data can use any single free blocks. Press buttons; watch the grid and the verdict.

Toy scale (64 blocks vs millions), but the allocation rule that causes the bug is the real one. The exporter’s live signal — average free extent < 16 blocks (64 KiB) — is the early warning; the crash itself needs the free space fragmented below the cluster size.
